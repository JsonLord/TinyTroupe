# Agent-to-Agent (A2A) Protocol in TinyTroupe

In TinyTroupe, agent-to-agent (A2A) communication is managed through an implicit protocol based on a system of **Actions** and **Stimuli**. The environment (`TinyWorld` or `TinySocialNetwork`) acts as a central router or server that mediates these interactions.

## Core Components of the Protocol

### 1. Actions
Actions are what agents *do*. They are generated by an agent's `act()` method and represent an intention to affect the environment or another agent.

- **Structure:** Actions are dictionaries, typically containing a `type`, `content`, and an optional `target`.
- **Common Action Types:**
  - `THINK`: An internal action that represents an agent's thought process. It doesn't directly affect other agents but is recorded in the agent's memory.
  - `REACH_OUT`: + 'Keyword' = An action to establish contact or accessibility with another agent. = Open Situation Room A2A chatroom between tinyPersona and DeepAgent Cli
  - `DONE`: Signals that an agent has no further actions to take in the current step.

### 2. Stimuli
Stimuli are what agents *perceive*. They are the result of an action performed by another agent or an event in the environment. When an agent receives a stimulus, it processes it and updates its internal cognitive state.

- **Structure:** Stimuli are also dictionaries, typically containing a `type`, `content`, and a `source`.
- **Common Stimulus Types:**
  - `CONVERSATION`: The result of a `TALK` action from another agent.
  - `SOCIAL`: Represents a non-verbal social cue or event.

### 3. The Environment as a Router
The `TinyWorld` class is crucial for the A2A protocol. It receives actions from agents and translates them into the appropriate stimuli for the target agents.

## How it Works: An Example Flow

Here is the step-by-step process of a simple `TALK` interaction between two agents, Lisa and Oscar:

1.  **Action Generation:** Lisa's `act()` method decides to communicate with Oscar. It generates a `TALK` action dictionary:
    ```json
    {
      "type": "TALK",
      "content": "Hi Oscar, how are you?",
      "target": "Oscar"
    }
    ```
2.  **Action Handling:** The `TinyWorld` environment receives this action from Lisa during its simulation step.
3.  **Stimulus Creation:** The environment's `_handle_talk` method identifies "Oscar" as the target. It then creates a `CONVERSATION` stimulus intended for Oscar:
    ```json
    {
      "type": "CONVERSATION",
      "content": "Hi Oscar, how are you?",
      "source": "Lisa"
    }
    ```
4.  **Stimulus Delivery:** The `TinyWorld` calls Oscar's `listen()` method, passing the `CONVERSATION` stimulus as an argument.
5.  **State Update:** Oscar processes the stimulus, adds the message to his episodic memory, and updates his cognitive state. This new information will influence his subsequent actions.

## Feedback and Suggestions for Formalization

The current A2A protocol is functional and flexible. However, to support more complex and robust interactions, it could be formalized and extended.

- **Formalize with a Registry:** Create a dedicated registry (e.g., a Python Enum or a dictionary) that defines all valid `Action` and `Stimulus` types. This would enforce consistency and prevent the use of arbitrary, undefined types.

- **Introduce More Expressive Actions:** The protocol could be enriched with more specific action types to make agent intentions clearer:
  - `REQUEST_INFORMATION(question)` 
  - `PROVIDE_INFORMATION(data)` 
  - `CONFIRM_ACTION` 
  - `DENY_ACTION` 

- **Implement Explicit Success/Failure Responses:** Currently, an agent doesn't receive direct feedback on whether its action was successful. You could enhance the protocol by making the environment send a confirmation stimulus back to the originating agent.
  - **Example:** When Lisa sends a `TALK` message to Oscar, the environment could send a `MESSAGE_DELIVERED` stimulus back to Lisa upon successful delivery, or a `MESSAGE_FAILED_TARGET_NOT_FOUND` stimulus if Oscar isn't accessible. This would enable more sophisticated, stateful interactions and error handling.
